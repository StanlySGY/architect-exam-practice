- 模板启发式命中 `scenarios` 20/20、`examFocus` 18/20、`why` 2/20；`how`、`confusions` 未命中当前已知模板信号。模板命中是人工复核提示，不代表事实错误；未命中也不证明讲解充分。
- 第一题有 5/20 是通用复述题、15/20 是较具体问题；第二题 15/20 已围绕架构或具体方法提出问题，2/20 是数据流模板，3/20 是通用“五个问题”架构分析脚手架。总体自检比完全通用模板更有针对性，但仍可进一步转成案例判定、画图、错误识别、权衡与证据题。
- **关键标准边界：** ISO/IEC/IEEE 42010:2022 规定架构描述（AD）的结构与表达，不规定架构创建/使用/管理的过程、架构方法、模型、工具或技术；ISO/IEC/IEEE 12207:2026 于 2026-04 发布，才是覆盖软件获取、供给、开发、运行、维护、退役的生命周期过程框架，并允许过程并发、迭代和递归应用。现有 7.1.2 的 42010 evidence 不能单独证明“架构活动贯穿全生命周期”。
- **关键行业边界：** Flink 的 event time/window/watermark 文档说明实时事件计算语义，不证明体育热点业务、广告归因、实时预算或反作弊系统的业务指标。IAB Tech Lab 的 Event & Conversion API v1.0 于 2026-01-13 发布，测量指南还涉及曝光、可视曝光、无效流量、归因窗口披露等领域要素；需要与流计算底层机制配套，而不能以计算引擎文档替代行业测量规范。
- 架构风格分类存在“层次不完全一致”的问题：pipe-and-filter 属于数据流组织；main program/subroutine 与 object-oriented 属于显式调用/返回组织；repository/blackboard 是数据中心组织；interpreter 属于虚拟机模式；event systems 属于隐式调用/事件组织。它们是帮助分析结构和交互的分类视角，不意味着每个真实系统只属于一个风格或必须严格套用唯一分类表。
- 复用主题需区分“资产抽象层次”和“复用策略”：架构决策、模式、参考架构、框架、构件、产品线资产不是严格同层级、互斥的类型；白盒/灰盒/黑盒描述复用者对内部实现的可见/可修改程度；机会式/系统化描述复用组织方式。分类维度不能混排。

| 7.5.1 | 领域参考架构描述某领域系统的共同结构、功能、质量属性和变化点；SEI SPL 资料支持相关产品共享受管理的共同性与变化性。 | 参考架构不是具体产品架构，也不是必须逐项照搬的完整蓝图；它为领域内产品提供可复用结构、概念、接口/机制和变化点。领域参考架构与软件产品线高度相关，但两者不等同：产品线还需要范围界定、核心资产、变体模型、生产计划、治理和产品开发能力。建议明确“不适用的领域边界”和项目偏离的理由。 |
| 7.5.2 | 领域工程分领域分析、领域设计、领域实现：识别共性/可变性，形成领域架构/资产并落实；SEI SPL 将核心资产开发与产品开发作为两类本质活动。 | 教材阶段划分可能因领域工程方法不同而异，不应把三阶段写成所有方法唯一固定过程。分析的产物可能包括领域范围、特征/共性与可变性模型；设计产物包括参考架构、核心资产和变体机制；实现/资产化包括构件、测试、文档和生成/组装机制。还需与应用工程/产品开发区分，产品需求对核心资产的反馈可能调整领域范围和变体模型。 |

## 来源清单与适用边界

1. **软件生命周期与架构实践**
   - ISO/IEC/IEEE 12207:2026（Final, 2026-04）：https://www.iso.org/standard/90219.html 。生命周期过程框架涵盖获取、供给、开发、运行、维护和退役；支持并发、迭代与递归应用；不强制某一种生命周期模型或开发方法。
   - ISO/IEC/IEEE 42010:2022：https://www.iso.org/standard/74393.html 。规定架构描述结构/表达要求，区分架构与描述工件；明确不规定架构创建/管理过程、方法、模型、工具。
   - ISO/IEC/IEEE 14764:2022：https://www.iso.org/standard/80710.html 。定义软件维护过程和活动；明确不覆盖通常由运行者负责的备份、恢复和系统管理等运行活动。
   - CMU/SEI Software Architecture：https://www.sei.cmu.edu/software-architecture/ 。介绍架构设计决策、质量属性、涉众沟通、早期风险识别和持续演化。
   - CMU/SEI Software Architectures and Acquisition：https://www.sei.cmu.edu/library/software-architectures-and-acquisition/ 。架构中心开发的迭代活动包括理解使命驱动、涉众需求、架构选择、文档沟通、评估、实现与一致性验证；说明早期架构决策的长期影响。

2. **架构风格与模式分类**
   - CMU/SEI *Developing Software Product Lines*（2020）架构模式分类资料：https://www.sei.cmu.edu/documents/1602/2020_011_001_650228.pdf 。展示 data-centered、virtual-machine、call-return（explicit invocation）、data-flow 等模式族及示例；分类用于学习比较，不等于真实架构只能选一个。
   - CMU/SEI *Architectural Styles and the Design of Network-based Software Architectures*（旧文）：https://insights.sei.cmu.edu/documents/232/1994_019_001_30085.pdf 。支持 pipe-and-filter、数据中心和事件系统等经典风格存在；具体运行语义需要结合实现。
   - ISO/IEC/IEEE 42010:2022 同上，用于区分架构描述、视图/视角概念与实际风格选择。

3. **软件复用与产品线**
   - CMU/SEI Software Product Lines Collection：https://www.sei.cmu.edu/library/software-product-lines-collection/ 。软件产品线定义为共享受管理特征、满足特定市场/任务需求、由共同核心资产按规定方式开发的一组软件系统。
   - CMU/SEI *Variability in Software Product Lines*（2005）：https://www.sei.cmu.edu/library/variability-in-software-product-lines/ 。共同核心资产的变体需计划和显式管理；可变性管理不当会导致机制重复、不兼容或漏掉需求。
   - CMU/SEI *A Framework for Software Product Line Practice*（2012 PDF）：https://resources.sei.cmu.edu/asset_files/WhitePaper/2012_019_001_495381.pdf 。区分 core asset development/domain engineering 与 product development/application engineering；二者可按组织情况交错或并行，产品反馈可影响核心资产范围。
   - CMU/SEI *Guidelines for Developing a Product Line Production Plan*（2002）：https://www.sei.cmu.edu/library/guidelines-for-developing-a-product-line-production-plan/ 。生产计划说明如何正确使用核心资产组装特定产品；计划形式因组织而异。

4. **广告测量与实时流处理**
   - IAB Tech Lab Measurement Pillar：https://iabtechlab.com/standards/measurement/ 。列出 Event & Conversion API（ECAPI/CAPI）v1.0，2026-01-13 发布，用于标准化广告主与平台/合作方之间的营销/转化事件通信；也列出 OM SDK 等广告曝光测量资料。
   - IAB/MRC Retail Media Measurement Guidelines Explainer（2024-01）：https://www.iab.com/wp-content/uploads/2024/01/IAB-MRC-Retail-Media-Measurement-Guidelines-Explainer-January-2024.pdf 。讨论曝光/可视曝光、一般/复杂无效流量、归因窗口披露和 outcome measurement；属于零售媒体指南摘要，不替代完整 MRC 标准或广告主具体归因协议。
   - Apache Flink *Timely Stream Processing*（stable）：https://nightlies.apache.org/flink/flink-docs-stable/docs/concepts/time/ 。区分 event time、processing time、水位线、窗口及迟到事件；不定义广告/体育行业业务归因和商业指标。
   - Apache Flink *Streaming Analytics*（stable）：https://nightlies.apache.org/flink/flink-docs-stable/docs/learn-flink/streaming_analytics/ 。展示事件时间用于可重复历史分析及窗口处理；结果仍取决于输入、窗口和迟到策略。
   - Apache Flink *Generating Watermarks*（stable）：https://nightlies.apache.org/flink/flink-docs-stable/docs/dev/datastream/event-time/generating_watermarks/ 。用于时间戳/水位线生成配置，需按项目锁定的 Flink 版本核对。

## 下一步教学修订建议（草案，未写回 JSON）

1. **生命周期与架构价值**：将 12207:2026 作为生命周期过程依据，将 42010:2022 作为架构描述依据，SEI 作为架构实践跨阶段的证据；补充“早期决策为何昂贵、质量属性为何需要早评估”的因果说明。
2. **迭代闭环与原型**：给出需求—架构—实现—测试—运行反馈的闭环图；将架构原型按待验证假设、实验边界、度量、结论、剩余风险记录，明确原型不是生产验收。
3. **架构风格分类**：建立“组织结构/控制流/数据流/连接交互”分类对照表，统一 pipe/filter、call-return、repository/blackboard、interpreter/VM、event/implicit invocation 的定义；设计题让考生识别依赖、数据流和控制流，而非只背名字。
4. **架构演化**：以维护类型、需求演化、现代化和运行反馈区分触发原因；加入 API/schema 兼容、数据库迁移、分阶段部署、回滚和架构一致性验证。
5. **复用与产品线**：先建立复用资产层次分类，再讲黑/灰/白盒与机会/系统化复用；补共同性/可变性、核心资产开发、产品开发、生产计划、治理与 ROI/TCO；让学生识别过度通用化和版本分叉的代价。
6. **行业数据应用**：为体育/新闻补事件 ID/事件时间/业务修订、热点窗口与历史画像指标；广告场景加入曝光、可视曝光、点击、转化、无效流量、归因窗口和离线最终对账，区分 Flink 计算语义与广告领域测量规则。
7. 将第二道自检升级为画图、辨析、故障推理和权衡题；所有单元在教材版次/页码核验前继续保持 partial，不更新正文、evidence 或状态。
