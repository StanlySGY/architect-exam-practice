## 逐项复核

| 单元 | 当前主题与 evidence 有效范围 | 发现 / 后续修订方向 |
|---|---|---|
| 9.5.2 | 运行剖面描述实际使用行为/操作的相对频率。 | 需界定用户、操作、输入的建模粒度。SEI 定义为特定环境下行为的相对频率/概率列表；实际分布应由遥测、用例或任务数据建立，不能臆造概率。原 SEI 专题链接本轮不能直接读取；可用 CMU/SEI-2001-TR-022 第 3.5、4.5 节作补充候选来源。 |
| 9.5.3 | 按运行剖面分配测试，同时补充关键、边界和安全场景。 | 分开讲“按使用概率加权的代表性测试”与“风险驱动的异常/边界测试”。随机抽样不能保证罕见高危路径被覆盖；分层抽样要说明变量和权重。 |
| 9.5.4 | 在约定配置和环境下测试并保留结果。 | ISO/IEC/IEEE 29119-1:2022 支持测试上下文、环境和数据管理等通用概念；现有 URL `https://www.iso.org/standard/22749.html` 与本轮查到的 29119-1:2022 官方页面不一致，正确官方入口为 `https://www.iso.org/standard/81291.html`。合同/用户文档的特定配置清单仍需教程依据。 |
| 9.6.1 | 可靠性评价可辅助测试终止、目标达成和发布决策。 | 方向合理，但模型输出不能自动等于发布批准。需结合数据代表性、模型假设、风险接受、合同验收和业务决策。 |
| 9.6.2 | 不存在适用于所有系统的最佳可靠性模型。 | 当前 NIST Reliability Glossary 只支持 reliability 术语，不能支撑模型选型。NIST SP 500-209 明确指出模型基于不同假设、没有普遍适用模型，并列出预测有效性、参数可测量性、假设质量、适用性、简单性、噪声敏感性和参数敏感性等选型因素。 |
| 9.6.3 | 可靠性数据涉及软件失效/错误数据和生命周期活动。 | “以失效数据为主”需限定模型及目标。NIST SP 500-209 指出有效的组织数据库需要开发与运行两类错误数据，也区分错误分析、产品质量度量与可靠性估计；不宜将失败事件记录写成唯一数据。 |
| 9.6.4 | 可靠性评估可支持目标预测、验收、发布和投入决策。 | NIST SP 500-209 将当前可靠性、目标预测、验收准则符合性、新功能/技术引入和安全认证列为估计用途。必须披露模型误差、数据代表性和不确定性，不能承诺确定的发布时间或必然达标。 |
| 10.1.2 | 架构定义/表达方式影响演化分析的关注对象。 | 先区分“架构”与“架构描述（AD）”。ISO/IEC/IEEE 42010:2022 区分实体架构和描述架构的 AD，并规定 viewpoint、model kind、ADL 等要求；不规定具体演化方法。现有链接路径异常，建议指向 `https://www.iso.org/standard/74393.html`。 |
| 10.2.1 | 顺序图对象/生命线的新增、删除会影响交互表达。 | UML 生命线表示交互中的参与者，不应直接等同于可独立部署的“构件实体”。新增/删除只是可能的图模型编辑，需结合 part、role、connectable element 等语义说明。 |
| 10.2.2 | 消息表达参与者之间通信及交互顺序。 | 当前证据范围基本合理。需区分消息方向、发送/接收事件和同步/异步语义；图上时序关系不等于实际时延、并发保证或网络性能。 |
| 10.2.3 | 组合片段描述交互控制结构。 | **明确分类错误：`ref` 不是 `InteractionOperatorKind` 操作符。** UML 2.5.1 将 `InteractionOperatorKind` 和 `InteractionUse` 分别定义；顺序图 `ref` 表示复用/引用另一段 Interaction。常见组合片段操作符有 `alt`、`opt`、`loop`、`break`、`par` 等，另外还有 `seq`、`strict`、`critical`、`neg`、`assert`、`ignore`、`consider`。不要把常见列表误作完整枚举。 |
| 10.2.4 | 交互约束/守卫条件限制消息或片段的合法执行。 | 区分 UML Constraint、InteractionConstraint 与 operand guard；任意自然语言说明不会自动获得可执行形式语义。应明确约束对象和可判定条件。 |
| 10.3.1 | 根据变化发生时系统所处状态划分四个时期。 | ISO/IEC/IEEE 14764:2022 说明软件维护过程和维护类型，且明确不覆盖软件运行活动；不能据此证明“四个时期”分类。必须回到指定教材原页核对，继续 partial。 |
| 10.3.2 | 系统停机后修改架构/实现，再重新部署和启动。 | ISO 14764 支持维护生命周期语境，但不规定所有离线变更都必须完整停机、修改、重启。停机窗口、数据迁移、回滚和恢复验证应作为实施条件，而不是概念必然步骤。 |
| 10.3.3 | 系统运行中变更构件/配置，尽量保持服务连续。 | 渐进迁移、兼容接口、分阶段切换和回滚可降低中断风险，但不能保证零停机。应补充兼容窗口、数据一致性、状态迁移和切换/回退条件。 |
| 10.5.1 | 有演化步骤和中间版本时分析变化轨迹。 | Git 日志可记录提交时间线，但不等于架构质量度量。若要“度量”，须定义指标、基线、工件版本、映射关系和采集规则；否则宜写“追踪/回顾变化”。 |
| 10.5.2 | 只有前后版本时，匹配结构并做差异分析。 | Git diff 比较提交、索引和工作树中的内容差异；文本差异无法自动恢复架构意图，也不保证识别构件对应关系和间接影响。结构匹配需要稳定标识、模型级差异和人工分类。 |
| 10.6 | 网站架构随业务、流量和数据规模变化而演进并权衡复杂度。 | Azure 资料支持根据约束选择架构风格并权衡收益/挑战，不支持所有网站按单体—分层—微服务固定顺序演进。应让测量瓶颈、团队能力和运维成本成为案例中的决策依据。 |
| 10.7.2 | 通过修改规则、类型、影响范围和副作用分析控制变更。 | ISO 14764 支持受控维护过程，但未规定分析表的唯一格式。建议明确变更请求、理由、受影响视图/构件、依赖、风险、验证、批准和回滚责任。 |
| 10.7.3 | 对架构模型、决策、配置和实现映射实施版本控制。 | Git/配置管理支持保存历史、比较和恢复工件，但不能自动保证架构模型、决策记录、配置与代码映射正确。需要共同基线、版本关联、变更追溯和一致性检查。 |

## 来源清单与适用边界

1. John D. Musa, “Operational profiles in software-reliability engineering”, IEEE Software, 1993, [DOI 10.1109/52.199724](https://doi.org/10.1109/52.199724)。摘要支持系统使用方式的量化描述及按使用分配测试；本轮检索到的是论文元数据/摘要页面，不是 IEEE 全文。
2. Carnegie Mellon SEI, [Testing a Software Product Line, CMU/SEI-2001-TR-022](https://insights.sei.cmu.edu/documents/661/2001_005_001_13889.pdf)，第 3.5、4.5 节定义运行剖面为特定环境中行为相对使用频率的概率列表，并展示按频率分配测试的示例。它讨论产品线测试，外推到一般系统时需限定场景。
3. NIST SP 500-209, [Software Error Analysis](https://www.govinfo.gov/content/pkg/GOVPUB-C13-544cb4761091db86f21c05bcb2647157/pdf/GOVPUB-C13-544cb4761091db86f21c05bcb2647157.pdf)，1993。第 5.5 节说明无普遍适用的软件可靠性估计模型及模型选择因素；同时说明有效数据库需包含开发和运行错误数据。年代较早，适合作为方法论补充，不替代新版标准或指定教程。
4. [ISO/IEC/IEEE 29119-1:2022](https://www.iso.org/standard/81291.html)，软件测试通用概念；支持测试上下文、环境、数据等术语范围，不支持课程中特定合同/用户文档配置清单的无条件背书。
5. [ISO/IEC/IEEE 14764:2022](https://www.iso.org/standard/80710.html)，软件维护生命周期过程；官方摘要明确其描述维护过程/活动/任务和维护类型，且不覆盖软件运行活动。
6. [ISO/IEC/IEEE 42010:2022](https://www.iso.org/standard/74393.html)，区分实体架构与架构描述，规定 AD、viewpoint、model kind 等，不规定架构创建或管理的具体方法。
7. [OMG UML 2.5.1 规范](https://www.omg.org/spec/UML/2.5.1/PDF) 与 [OMG 机器可读规范目录](https://www.omg.org/spec/UML/machine-readable)。规范目录将 `InteractionOperatorKind` 与 `InteractionUse` 分列；机器可读元模型把 `ref` 记法映射到 InteractionUse。本轮 PDF 图像服务对 UML 文件返回体积限制，未取得相关标准定义页截图。
8. [Microsoft Azure Architecture Styles](https://learn.microsoft.com/en-us/azure/architecture/guide/architecture-styles/)，支持架构风格的适用条件、收益和挑战，不提供固定阶段演进规律。
9. [Git log](https://git-scm.com/docs/git-log)、[Git diff](https://git-scm.com/docs/git-diff) 官方文档支持版本历史和差异比较的工具能力；不代表工具能自动度量架构质量或恢复设计意图。
