# 批次 C 第 11 批 20 个学习单元来源与教学质量初审（2026-11-06）

## 结论与范围

本批按只读工作队列复核 20 个 `partial` 单元：7.5.4、8.1.3、8.2.2、2.1、7.1.1、7.2.1、7.2.4、7.2.6、7.2.7、8.1.1、9.1.1、9.2.1、2.2、2.3、2.9、7.3.1、10.1.1、10.4.1、10.4.2、10.4.3。

**20 个单元全部继续保持 `partial`。** 本轮检查 what、evidence 的 claim/scope、why/how/confusions/scenarios/examFocus/pitfalls 和 selfChecks，并与 ISO、NIST、CMU/SEI、NASA、PMI 等来源交叉复核。来源检查只确认对应 claim/scope 的有限事实，不等于教材版次/印刷页码核验，也不构成人工签字或整单元事实覆盖认证。本轮不写回课程 JSON。

## 工作队列与共性信号

- 本批排名 201–220，20/20 单元均有 6 个非空教学字段。19/20 只有 1 条结构有效的命题级 evidence；2.1 有 2 条。20/20 的 evidence 均来自单一 host，不能据此推断来源相互独立或覆盖全部教学主张。
- evidence 日期：8 个单元为 2026-10-09，12 个为 2026-10-10。
- 本批命中已知模板信号的单元仅 4/20：7.5.4（scenarios、examFocus）、8.1.3（scenarios、examFocus）、8.2.2（scenarios、examFocus）、2.1（why、examFocus）。模板检测是有限的文本启发式；不命中不代表教学充分，命中也不自动代表内容错误。
- 8.1.3 与 8.2.2 的 why/how/confusions/scenarios/examFocus 大量沿用“围绕 what 展开”的通用包装，第二道 selfCheck 也复用质量场景分析脚手架。10.4.1–10.4.3 的 why、how、scenarios、examFocus、pitfalls 则多为把“演化成本控制/进度可控/风险可控”代入通用模板；pitfalls 自身还提示其维护原则解释并非教材原文。它们可以保留作复习提示，但不应被误认成教材定义或已经核实的过程模型。
- **标准用途必须分开：** ISO/IEC/IEEE 42010:2022 规范架构描述的结构与表达，不规定架构创建、使用或管理的方法；ISO/IEC/IEEE 12207:2026 是软件全生命周期过程框架；ISO/IEC/IEEE 14764:2022 聚焦软件维护过程，不能替代架构演化全貌。10.1.1 当前只引用 14764，属于证据范围偏窄。
- **领域工程阶段不是通用强制清单：** 7.5.4 的七步链条可以作为学习用活动分解，但 SEI 产品线资料只证明核心资产建设、变体管理、产品线范围/领域分析及产品开发等实践的重要性，不证明这七项是所有领域工程方法统一且严格线性的阶段。
- **架构质量评估分类需避免过度定型：** SEI CMU/SEI-96-TR-036 明确讨论场景、问卷、检查表和度量等评估方式；当前 8.2.2 的“场景、度量、模型、经验/检查表”可以是教材归纳，但该证据没有把“模型”作为同层级独立分类来定义，也没有证明这些类别互斥或穷尽。
- **基础知识证据的粒度不足：** 2.1 的 NIST hardware/software 术语表仅支持基本定义；2.2 的 NIST system component 仅支持组件可以作为较大系统中的可识别组成部分；2.3 的操作系统术语只支持操作系统的基本作用；2.9 的 ISO/IEC 25010:2023 是产品质量模型。以上来源都不能单独支撑 CPU/存储/总线细节、软件分类全表、性能公式/容量模型或具体设计结论。

| 7.2.7 | 架构文档评审以涉众及其工作需要为中心，检查表达缺口；SEI CMU/SEI-2009-TN-030 明确说明该方法不是完整架构评估框架。 | 当前主张基本准确，但“架构评审”应防止与技术架构评估混用。文档评审关注信息是否足以让涉众理解和使用；技术评估还需验证质量属性、风险、关键决策和运行行为。建议将评审发现记录为问题、影响、责任人、证据和关闭条件，并明确“文档评审通过≠系统质量目标已被证明”。 |

| 2.2 | 主张涵盖处理器、存储器、总线、接口和外设；现有 NIST system component 只定义较大系统中可识别的硬件/软件/固件组件及其输入输出/功能。 | evidence 粒度明显不足。建议补充指定教材中的计算机组成、存储层次、总线互连和 I/O 系统资料；区分 CPU/缓存/主存/外部存储的访问特征、容量与成本权衡，区分总线/互连协议和设备接口。不要让一个“system component”术语表条目承担所有硬件结构知识。 |
| 2.3 | 主张列出 OS、数据库、文件系统、网络协议、中间件、构件和应用软件；NIST OS 术语只支持操作系统提供基础运行/资源管理服务。 | 证据只验证列表中的操作系统概念，不能证明其他类别的定义、边界或相互关系。建议每种软件分别用职责、接口/抽象、典型数据对象和依赖关系说明；数据库不等于文件系统，协议不是一个操作系统“部件”，中间件也不自动包含应用业务。可增加“一个请求从应用到网络/数据库/存储经过哪些软件层”的辨析题。 |

| 7.3.1 | SEI Garlan/Shaw 1994 软件架构入门资料支持架构风格以构件/连接件词汇及其组合约束描述一类系统组织方式，并可组合多种风格。 | 核心定义有历史基础资料支持。需明确风格不是某个具体产品、框架或完整系统实例；分析风格要落到构件职责、连接件语义、组合约束和质量属性代价。1994 报告是经典基础文献，不应被误用为当代所有架构风格分类的完整目录。 |
| 10.1.1 | 当前把架构演化概括为需求、技术、环境和质量目标变化下的结构调整；ISO/IEC/IEEE 14764:2022 只支持软件维护过程及其管理。 | 现有 evidence 对“架构演化”覆盖不足，不能把维护等同于架构演化。SEI 2023 报告更直接指出架构决策和跨质量属性分析应持续进行，且不在代码写完或发布时结束；ISO/IEC/IEEE 12207:2026 则提供覆盖开发、运行、维护和退役的生命周期过程框架。建议区分局部代码重构、维护变更、接口/数据/部署结构调整、需求驱动的架构迁移，并记录影响范围、兼容窗口、演进路径、风险和验证结果。 |
| 10.4.1 | 成本控制要求比较修改、测试、部署、兼容、迁移和后续维护的全生命周期成本；现有 ISO 14764 evidence 仅支持维护活动需计划/执行/评价及其生命周期背景。 | “修改—测试—部署—兼容—迁移—后续维护”的具体成本拆分是合理的工程化检查表，但不是当前证据证明的标准固定分类。建议说明估算范围、直接/间接成本、一次性/持续成本、迁移期双轨运行、停机与回滚成本和未来维护负担；若写成本模型/公式，需另给来源和假设。pitfalls 中已承认本单元原则名称仍待教材核对，应保留这条限制。 |
| 10.4.2 | 进度可控强调将维护变更拆成可估算和可验证任务、管理依赖与验收；evidence 包含 ISO 14764 和 PMI 项目进度管理资料。 | PMI 来源可支持活动分解、依赖识别、持续时间/资源估算、里程碑和进度跟踪；14764 只提供维护生命周期背景。进度计划不等于按期保证，仍受范围变更、资源可用性、估算不确定性和外部依赖影响。建议通过依赖图、关键路径/缓冲、验收门槛和变更控制演练，把一般项目进度管理与维护专属流程分开。 |
| 10.4.3 | 风险可控要求识别维护中的故障、迁移、兼容、安全和回滚风险；evidence 包含 ISO 14764 与 ISO 31000:2018。 | ISO 31000:2018 支持组织层面的风险识别、分析、评价、处理、监视和沟通；它不定义软件维护的专用风险清单或自动量化阈值。建议说明每个风险的触发条件、影响、可能性、责任人、处理策略、残余风险和监控信号；回滚是可能的缓解手段之一，不是所有迁移都可逆，也不能替代数据恢复/兼容验证。 |

## 来源清单与适用边界

1. **产品线/领域工程**
   - CMU/SEI, [Software Product Lines Collection](https://www.sei.cmu.edu/library/software-product-lines-collection/)。支持软件产品线与核心资产建设；不规定本批七阶段为唯一领域工程过程。
   - CMU/SEI, [Variability in Software Product Lines](https://www.sei.cmu.edu/library/variability-in-software-product-lines/), CMU/SEI-2005-TR-012。支持核心资产显式可变性建模与治理。
   - CMU/SEI, [Product Line Analysis: A Practical Introduction](https://www.sei.cmu.edu/library/product-line-analysis-a-practical-introduction/), CMU/SEI-2001-TR-001。支持产品线需求建模、对象/用例/特征建模的实践示例；其报告自身说明分析实践仍在演进。
2. **质量属性与架构评估**
   - CMU/SEI, [Reasoning About Software Quality Attributes](https://www.sei.cmu.edu/library/reasoning-about-software-quality-attributes/)。支持质量属性场景用于精确定义属性需求，并说明通用场景是生成具体场景的模板。
   - CMU/SEI, [Achieving Product Qualities](https://www.sei.cmu.edu/library/file_redirect/2003_005_001_14213.pdf/), CMU/SEI-2003-TR-004。列出质量属性场景六部分：刺激源、刺激、环境、制品、响应、响应度量。
   - Barbacci、Klein、Weinstock, [Principles for Evaluating the Quality Attributes of a Software Architecture](https://www.sei.cmu.edu/library/principles-for-evaluating-the-quality-attributes-of-a-software-architecture/), CMU/SEI-96-TR-036（1997）。讨论场景、问卷、检查表和度量；不是唯一穷尽分类。
   - CMU/SEI, [Attribute-Driven Design Method Collection](https://www.sei.cmu.edu/library/attribute-driven-design-method-collection/)。ADD 输入包括已知功能需求、质量属性需求与约束，并采用递归分解。
   - CMU/SEI, [Views and Beyond Collection](https://www.sei.cmu.edu/library/views-and-beyond-collection/)。支持按涉众关注点选择架构视图和记录跨视图信息。
   - Nord 等, [A Structured Approach for Reviewing Architecture Documentation](https://www.sei.cmu.edu/library/a-structured-approach-for-reviewing-architecture-documentation/), CMU/SEI-2009-TN-030。其说明该文档审查方法不是完整技术架构评估框架。
3. **架构、生命周期与风格**
   - [ISO/IEC/IEEE 42010:2022](https://www.iso.org/standard/74393.html)：架构描述结构/表达要求；不规定架构方法。
   - [ISO/IEC/IEEE 12207:2026](https://www.iso.org/standard/90219.html)：2026-04 发布的软件生命周期过程框架，涵盖获取、供给、开发、运行、维护和退役，并支持并发、迭代和递归应用。
   - [ISO/IEC/IEEE 14764:2022](https://www.iso.org/standard/80710.html)：软件维护过程与活动指导；范围不等于完整架构演化过程。
   - CMU/SEI, [A Holistic View of Architecture Definition, Evolution, and Analysis](https://www.sei.cmu.edu/library/a-holistic-view-of-architecture-definition-evolution-and-analysis/), CMU/SEI-2023-TR-004。支持架构决策和跨质量属性分析持续贯穿实现发布之后。
   - Garlan & Shaw, [An Introduction to Software Architecture](https://www.sei.cmu.edu/library/an-introduction-to-software-architecture/), CMU/SEI-94-TR-021。经典架构风格、构件/连接件与组合约束基础文献。
4. **计算机基础、可靠性与性能**
   - NIST CSRC Glossary：[hardware](https://csrc.nist.gov/glossary/term/hardware)、[software](https://csrc.nist.gov/glossary/term/software)、[operating system](https://csrc.nist.gov/glossary/term/operating_system)、[system component](https://csrc.nist.gov/glossary/term/system_component)、[reliability](https://csrc.nist.gov/glossary/term/reliability)。术语条目只支持各自明确的定义，不能扩展为完整硬件/软件课程。
   - [NASA-TM-104799](https://ntrs.nasa.gov/citations/19950005501), *Software analysis handbook: Software complexity analysis and software reliability estimation and prediction*（1994）。支持软件可靠性定量估计用途；模型和公式仍应按教材与输入数据单独核验。
   - [ISO/IEC 25010:2023](https://www.iso.org/standard/78176.html)：定义 ICT/软件产品质量模型，用于质量属性的规定、测量与评价；不提供具体系统性能公式。
5. **维护项目管理与风险**
   - PMI, [Project management from the middle](https://www.pmi.org/learning/library/project-management-middle-five-stages-6969) 及 [Four Ways Project Schedules Are Limited](https://www.pmi.org/learning/library/four-ways-project-schedules-limited-7265)：支持工作分解、依赖、工期/资源估算、里程碑和计划不确定性。
   - [ISO 31000:2018](https://www.iso.org/standard/65694.html)：ISO 页面确认该版 2023 年复审后仍为当前版本；提供组织风险识别、分析、评价、处理、监视和沟通的指南。
