# AI Agent 与 Super-agent 架构设计（前沿拓展）

> 专题定位：可选拓展，不是考试大纲新增章节，不改变官方教程 20 章结构，也不计入零基础路线原有约 144 小时主线。目标是用一个现代 Agent 平台案例，练习把系统架构、事件驱动、分布式处理、异步通信、云原生、软件可靠性和安全知识组合起来。

更新日期：2026-11-03

## 1. 与考试大纲的关系

《系统架构设计师考试大纲》（2022 年审定通过）及《系统架构设计师教程（第 2 版）》包含软件架构设计、系统建模与评估、中间件、信息安全、软件可靠性、人工智能及未来信息技术等知识。本专题涉及的基础原理可以映射到这些考查范围；但 **Agent、Super-agent、Router / Worker、Trigger / Thread、Inline / Spill、Chain of Recall 等名称不应标注为大纲明确列出的独立必考术语**。

本专题分层使用：

- **考试基础（优先掌握）**：分层与组件职责、事件驱动、消息队列/发布订阅、同步与异步、并发与负载调度、状态持久化、故障检测与恢复、幂等与安全控制。
- **架构迁移（理解并会分析）**：Router / Worker、任务 Thread、会话隔离、计算/状态/环境解耦、进度看门狗。
- **前沿术语（了解即可）**：Inline / Spill、Chain of Recall、投机执行、BYOM。理解其目的、机制、代价和适用条件，不要求背诵某个厂商实现细节。

## 2. 建议的学习目标

完成本专题后，应能：

2. 解释 Router / Worker 的职责边界，以及会话连续性和并发吞吐之间的权衡。
3. 设计 Trigger 到 Worker 的事件处理链路，说明过滤、订阅、去重、幂等、背压和死信处理。
4. 区分同步请求、异步任务和网络协议层全双工通信。
5. 解释计算、任务状态和执行环境解耦后，如何实现持久化、重启恢复和端侧执行。
6. 设计同时监控服务存活和任务进度的 Watchdog，并说明可靠性、安全与人工审批措施。

## 3. 核心架构

### 3.1 Agent 执行闭环

可将 Agent 抽象为“目标/指令 + 模型推理与规划 + 工具调用 + 上下文/记忆 + 持久状态 + 执行环境”。模型输出下一步行动，工具与外部系统交互，执行结果回到上下文并更新任务状态，直至完成、失败或等待人工。

不要把 Agent 等同于大模型本身。模型 API 只是推理能力；任务队列、权限、持久化、工具执行、审计和恢复仍需要工程系统提供。

### 3.2 Router / Worker

Router 面向人和全局状态，维护任务关联、接收多信道输入、分发任务和汇总结果；Worker 面向单一执行目标，具有隔离上下文和受控工具权限，独立运行并回报状态。

| 设计 | 优点 | 代价/风险 |
|---|---|---|
| 单会话承担所有任务 | 全局上下文连续、实现简单 | 串行阻塞、上下文混杂、吞吐受限 |
| 每件事都新建会话 | 并发高、任务隔离 | 全局关联丢失、重复协调、用户交互碎片化 |
| Router + Worker | 统一交互与全局协调，Worker 并行隔离 | 引入调度状态、消息一致性、资源配额和冲突治理 |

Router / Worker 是一种逻辑职责划分，不意味着每一层必须只有一个进程或一个模型会话。Router 是否使用轻量模型、Worker 是否使用更强模型，属于成本/效果决策，不是固定架构规则。

### 3.3 事件驱动与 Trigger / Thread

推荐链路：

消息来源 → 接入与身份校验 → 程序规则快速过滤 → 持久化事件队列 → 订阅/路由 → Worker → 结果事件 → Router 汇总与对外反馈

- Trigger：一次环境事件，例如消息、PR 评论或 CI 结果。
- Thread：同一个业务对象或话题下相关事件形成的连续事件流。
- Fast Path：已存在订阅关系，程序将后续事件直达订阅 Worker。
- Slow Path：没有订阅者或任务尚未认领，由 Router 结合规则/语义判断并分配 Worker。
- 程序过滤适合做确定性、低成本规则；模型判断适合处理语义歧义。不要把明显可由代码判断的噪声全部交给 LLM。

事件系统通常要处理重复投递、乱序、积压、消费者故障和重试。优先采用事件 ID/幂等键、Inbox 去重、有限重试、退避和死信队列。多数工程系统应按至少一次投递并确保业务幂等来设计，不要轻易声称端到端“恰好一次”。

### 3.4 异步任务与上下文预算

异步任务接口可先返回 taskId 和 accepted/started 状态，后台继续执行；进度、完成、失败或待人工处理通过事件/查询接口返回。前台继续接收新指令并不等于底层工具操作已经完成。

- Inline：将近期高概率使用的摘要和关键信息放入当前上下文。
- Spill：将低频、过长的信息保存在外部状态/存储中，只保留可授权读取的引用。
- Chain of Recall：通过稳定 ID 关联事件、Thread、Worker、项目和交付物，按需沿引用关系召回历史。

这几个术语描述的是应用层上下文管理策略。它们不是操作系统自动换页机制，也不能免除模型/程序检查引用有效性、权限、版本和召回完整性的责任。

### 3.5 计算、状态和环境分离

- 计算：可替换的 Agent 执行循环/Worker 进程。
- 状态：任务状态机、会话、事件偏移、检查点、工具结果和交付物元数据。
- 环境：代码仓库、文件、工具链、硬件、网络和凭据。

解耦后，计算实例可重启或扩缩容，任务状态可持久化恢复，执行环境可以位于云端或用户设备。BYOM（Bring Your Own Machine）可通过端侧 daemon 接入本地环境，但它会扩大信任边界：要使用双向认证、最小权限、短期凭据、沙箱、网络限制、操作审批、审计和撤销机制。

恢复不能只靠重新启动进程。需要定义检查点、状态机、租约/心跳、未完成副作用处理和恢复后的去重逻辑。

### 3.6 Watchdog 与可靠性

Watchdog 应位于主执行循环之外，形成独立控制回路。它至少需要区分：

- Liveness：进程/服务是否存活。
- Readiness：服务是否具备接收任务的条件。
- Progress：任务是否在合理期限内取得实质进展。
- Correctness：输出是否通过规则、测试或人工验收。

心跳只能证明某个组件仍能响应，不证明任务正确或持续推进。异常处理应包括超时、有限重试、指数退避、熔断、隔离、任务重新排队、检查点恢复和人工接管。应避免多个恢复控制器相互触发造成重启风暴。

### 3.7 安全与架构质量

重点关注身份与任务绑定、RBAC/ABAC、最小权限、工具白名单、代码执行沙箱、凭据隔离、提示词注入、数据脱敏、跨租户隔离、操作审计和人工审批。模型生成的文本不是权限凭证，Worker 不应天然拥有整个环境的高权限。

常用评价指标：任务完成率、P50/P95 端到端时延、队列等待时间、吞吐量、重复副作用率、恢复时间、人工介入率、单位任务模型成本和安全事件数。投机执行可以提前准备草稿/测试，但会消耗额外资源；结果必须隔离、可取消、可丢弃，不能未经审批执行不可逆操作。

## 4. 易混淆概念

| 概念 | 正确理解 | 不要混淆成 |
|---|---|---|
| Router / Worker | 全局交互协调与隔离任务执行的职责划分 | 必然是两个固定服务器/两个固定模型 |
| Fast / Slow Path | 程序直通与未认领事件的路由路径 | 处理器快慢路径或网络路由协议 |
| 异步 ReAct | Agent 任务启动、后台运行、结果回传 | TCP/HTTP 协议层的全双工 |
| Inline / Spill | 上下文内联与外部存储按需召回 | OS 自动分页/换页 |
| Chain of Recall | 基于 ID 和引用关系的关联召回 | 只靠向量检索的知识库 |
| 投机执行 | 结果未确定前先做可丢弃的准备工作 | CPU 分支预测的完整等价实现 |
| Watchdog Session | 监控任务进展并触发恢复的外部控制回路 | 单纯硬件看门狗定时器 |
| BYOM | 个人/企业设备提供受控执行环境 | 可以把云端权限无条件授予本地机器 |

## 5. 综合案例练习

### 题目：企业研发协作 Agent 平台架构设计

某软件企业准备建设研发协作平台，统一接入企业 IM、邮件、GitHub Pull Request 和 CI 系统。平台需要识别缺陷反馈、自动关联同一问题的讨论、并行执行复现/代码审查/测试任务，并将结果统一反馈给用户。

业务约束：

- 高峰期每分钟约 200 条外部事件，其中大量为无效通知。
- 单项复现或测试任务可能持续 10 分钟以上。
- 同一个缺陷可能同时出现在 IM、PR 和 CI 记录中。
- Worker 运行期间可能重启，任务不能因执行进程退出而全部丢失。
- 系统不得因重复事件创建重复 PR、重复发布或重复执行不可逆操作。
- 访问生产环境、合并代码和对外发送消息等高风险动作必须经过授权审批。

请回答：

1. 设计平台总体逻辑架构，说明 Router、Worker、事件队列、状态存储、执行环境和 Watchdog 的职责及主要数据流。
2. 说明如何使用事件过滤、Thread 关联、订阅路由和异步任务处理高并发与长时间运行任务，并避免重复执行。
3. 说明如何实现 Worker 异常后的任务恢复，以及如何保障代码仓库、凭据、外部系统和高风险操作的安全。
4. 分析该架构在性能、可用性、可维护性、安全性和成本方面的主要权衡，并给出可观测的评价指标。

### 参考答题要点

**第 1 问：** 多信道接入层进行认证、限流和事件标准化；事件总线负责持久化缓冲；规则过滤器先处理确定性噪声；Router 维护全局任务/Thread 关联并创建任务；Worker 池按任务类型隔离执行；状态库保存任务状态机、事件 ID、租约和检查点；对象存储保存日志和交付物；Watchdog 独立观察服务和任务进度。

**第 2 问：** 对事件来源、类型、仓库、PR/工单 ID 做规则过滤；将相同业务对象的事件关联到 Thread；已有订阅 Worker 走直通路径，新任务由 Router 分发；长任务通过异步任务 ID 返回，进度事件回传；消费者按至少一次投递设计，使用事件 ID、幂等键、Inbox 去重和任务状态机防止重复副作用；积压时通过背压、限流、扩容、优先级和死信队列治理。

**第 3 问：** 任务状态和执行计算分离，Worker 定期写检查点；通过租约/心跳识别失联 Worker；重新调度前先检查上次执行状态和外部副作用，避免盲目重放；采用有限重试、退避、超时、补偿或人工接管；执行环境按任务隔离，凭据通过秘密管理服务短期下发，实施最小权限、网络隔离、审计和审批；高风险操作由人类确认。

**第 4 问：** Worker 并行可提高吞吐但提高模型成本和协调复杂度；持久队列提高可靠性但增加存储和端到端时延；单 Router 简化全局协调但可能形成瓶颈，可批处理或分片；本地 BYOM 减少环境迁移但增加端侧信任与可用性风险。指标至少包括 P95 延迟、队列积压、任务成功率、重复副作用率、恢复时间、人工介入率、每任务成本和安全审计结果。

### 案例答题模板

业务目标与约束 → 质量属性场景 → 总体架构与组件职责 → 关键交互/数据流 → 可靠性机制 → 安全机制 → 性能与成本权衡 → 验证指标

## 8. 当前项目落地状态（2026-11-03）

本专题中的架构思想正在分阶段用于本地 Agent 工作区，当前 P0/P1 已落地：

- 本地确定性 Router：按单体、并行、对战策略生成显式执行计划，不额外调用模型。
- 隔离 Worker：独立任务使用独立模型请求上下文，支持并行执行，执行步骤带有稳定 ID。
- 依赖评审：对战评审是 Worker 结果之后的显式步骤，至少两个候选成功才执行。
- 输出质量门禁：检查非空答案、置信度范围和结构字段；门禁不替代资料核验、事实审查或人工评阅。
- 可观察与恢复：通过 SSE 展示计划、角色状态和门禁结果；保留单角色及评审独立重试，并在重试后刷新质量状态。
- 本机历史：用户主动保存时，按白名单保留计划和质量摘要；现阶段仍限当前浏览器 localStorage。
- 持久任务状态：独立 SQLite 表保存 taskId、幂等键摘要、请求白名单、状态机、租约、执行结果和有序事件日志。
- 断线恢复：SSE 订阅使用 Last-Event-ID 游标读取持久事件；客户端掉线不取消后台任务，重新连接可从最后已读事件继续。
- 取消与恢复：用户取消转为持久 cancel_requested 状态；后台 heartbeat 传播取消；租约过期后重新排队，最多两次执行尝试；终态任务保留 7 天。
- 任务访问控制：任务查询、列表、事件和取消均限定 owner_key；远程认证场景只将访问令牌 SHA-256 摘要作为归属键存储，不保存令牌本身。

当前尚未实现的 DSH 类能力：独立 Watchdog 的实质进度停滞检测、跨进程/多节点调度、事件 Trigger / Thread、多信道任务关联、上下文 Inline / Spill、动态模型路由和工具权限审批。现有持久任务使用单进程后台 Worker + SQLite 租约；不是分布式队列，也没有保证 exactly-once。

落地顺序建议：已完成持久任务状态与事件协议、断线恢复、显式取消和有限租约重试；下一阶段再引入独立 Watchdog、任务优先级/并发池和人工接管，最后评估事件触发器、上下文召回与成本感知模型路由。
